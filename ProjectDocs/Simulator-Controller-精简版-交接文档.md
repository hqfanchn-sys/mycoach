## 1. 项目目标与当前结论

用户希望基于开源项目 **Simulator Controller** 的官方源码，做一个供自己使用的精简版，当前主要面向 **iRacing**。原版功能和配置过于复杂，因此需要保留教练核心能力，简化操作，并保留今后的扩展空间。

第一版围绕 **A 游戏接入与赛道数据、B 驾驶教练、M 语音与大模型功能** 展开：本地程序采集和处理数据，**GPT-6.1 Sol 负责驾驶分析，GPT-Live 1 负责语音交流**。**主动逐弯提醒已明确加入第一版；本人实际线路与参考线路的叠图暂不做。**

当前已经完成原版功能和关键源码的静态审查、功能清单以及需求记录。文中列出的首版能力是待实现范围，不是已经交付的软件功能。

## 3. 第一版计划提供的能力

以下是目前讨论形成的首版核心能力。具体界面形式、默认参数和部分细项仍需收敛。

| 能力 | 用户可以怎样使用 | 对应功能与依赖 |
| --- | --- | --- |
| 自动识别驾驶环境 | 知道当前车辆、赛道、场次、圈数，让教练理解上下文。 | A02、A03，必要的会话数据。 |
| 按圈采集遥测 | 记录速度、油门、刹车、转向、挡位等游戏实际提供的数据。 | A05，以及游戏数据接入。 |
| 地图与弯道分段 | 将数据对应到具体弯道，并识别车辆正在接近哪个弯。 | A08、A09；后台需要这些能力，完整编辑界面可以简化。 |
| 驾驶知识与状态问答 | 讨论驾驶技术，结合当前数据解释问题。 | B01、B02、M；涉及新的驾驶分析时交给 Sol。 |
| 整圈复盘 | 询问这一圈主要有哪些问题、应先改进哪里。 | B04，共用遥测分析程序。 |
| 指定弯道分析 | 分析某个弯的刹车、入弯、弯中和出弯表现。 | B05，地图分段和对应遥测。 |
| 参考圈数据比较 | 与上一圈、自己的最快圈或可用的指定参考圈比较。 | B06，参考圈选择、保存、读取及数据对齐。 |
| 自然语音交流 | 提问、追问、要求解释得更简单、打断或重复说明。 | M 的相关交互能力，通过 Live 接入；实际交互效果需要联调。 |
| 主动逐弯提醒 | 接近弯道时，简短提示本弯应尝试的驾驶调整。 | B07，Sol 建议、本地位置触发和 Live 播报。 |
| 保存和读取训练数据 | 保存遥测与参考圈，之后加载继续分析。 | C、L 的共用能力；简单的数据选择入口即可，不自动纳入完整练习中心。 |
| 基本运行设置 | 设置音频设备、提示开关、模型和保存位置，查看连接状态。 | M、O 的必要部分。 |

典型使用流程：跑几圈 → 问“我最需要改哪个弯” → Sol 分析 → Live 解释 → 下一圈接近该弯时主动提醒 → 跑完后再比较是否改善。

参考圈需要有实际数据。可以先使用自己的有效圈；使用他人的参考圈时，需要取得格式与内容可用的数据。当前没有建立或购买职业车手参考圈库。

## 5. 模型分工与建议实现方式

### 5.1 已确定的职责

| 环节 | 负责方 | 职责边界 |
| --- | --- | --- |
| 采集、定位、数值计算、存储 | 本地程序 | 获取真实数据、按距离和弯道整理、计算指标、管理参考圈、触发提示。 |
| 驾驶分析与专业建议 | Sol | 根据数据解释整圈或弯道表现，比较参考圈，形成改进建议。 |
| 语音交流与表达 | Live | 接收语音需求、澄清问题、承接追问、说明已有分析、播报提示。需要新的驾驶判断时调用 Sol 分析。 |

用户语音提问 → Live 接收需求 → 本地提供相关数据与指标 → Sol 分析 → Live 说明结果。

本地计算仍然必要。选择“分析用 Sol”不意味着将所有原始高频采样或精确数值计算都交给模型；模型也不能代替游戏中的定位和计时。

### 5.2 主动逐弯提醒的建议方案

以下是已讨论的设计方向，尚未实现或测得实际延迟：

1. 使用已有完整圈或有效赛段数据，由 Sol 提前生成对应弯道的短建议。
2. 本地程序根据地图、分段和实时位置判断何时提示。
3. 到达合适位置后，由 Live 播报与该弯对应的建议。
4. 新圈完成或用户提出新问题时，按需要更新分析；已有结果可以复用。

实施时还需处理：结果尚未准备好、建议已经过期、车辆已通过弯道、用户正在说话、切换车辆或赛道后的旧结果清理，以及提示间隔。建议把“跳过过期提示”和“使用正确场次及圈次的数据”纳入验收。

OpenAI 官方文档已核对：Live 支持把推理与工具工作委托给后端；Sol 支持推理、工具调用和结构化输出。Sol 的工具调用应使用 Responses API。具体 Live 委托接法、音频传输、账户可用性及实际性能还未联调。[GPT-Live 1](https://developers.openai.com/api/docs/models/gpt-live-1) · [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

## 6. 强依赖与精简原则

A～O 是按用户功能划分的目录，不是可以整体删除的独立代码包。原版既有独立应用，也有共用库、数据文件、规则和后台程序。

| 要保留的功能 | 必要依赖 | 可以简化的部分 |
| --- | --- | --- |
| B 的遥测和逐弯分析 | A 的游戏接入、详细遥测、地图、弯道与直道分段。 | 地图显示窗口和复杂编辑流程；地图数据本身仍需存在。 |
| 整圈与参考圈比较 | 与 C 共用的遥测采集、分析及数据对齐能力。 | 完整曲线编辑、布局、缩放等窗口功能。 |
| 参考圈及配置读写 | L 的本地数据库、遥测与赛道资料读写。 | 车队同步、社区分享、庞大的数据库管理界面。 |
| B03 专项问题分析（若启用） | 与 G 共用的 IssueCollector 等问题采集与检测程序。 | 完整调校工作台和调校文件编辑器。 |
| B07 主动逐弯提醒 | 实时位置检测、提示任务调度、音频输出。 | 不需要为此启用完整 F 观察员或 N 自动化界面；相关共用后台程序仍可能需要保留。 |
| 方向盘按键通话（若选择） | N 的对应按钮输入与绑定能力。 | 其他硬件、动态平台、Stream Deck 和复杂控制模式。 |
| A＋B＋M 正常运行 | 公共助手框架、规则处理、任务调度、通信、配置和日志。 | O 的复杂向导、主题、启动动画和自动更新。 |

H 的 Solo Center 是练习与场次管理工作台：整理场次、驾驶段、圈次、轮胎及历史记录，并保存整场状态。当前首版只需要必要的数据保存和读取，未要求保留完整 H。

N 主要负责按钮、硬件、游戏菜单和外部软件自动化。M 的工具调用只能操作已经接入的能力；加入语音模型不自动获得进站控制或策略执行。

O 的设置界面可以缩小或使用预设值，但运行参数、必要依赖和错误记录仍要存在。自动更新可以不做；以后仍可能需要适配游戏或模型接口变化。

### 7.1 原版 AI 教练的原理

原版是一条混合处理链路：游戏数据采集 → 本地遥测特征提取 → 规则判断 → 大模型解释或生成建议 → 语音输出。

- `DrivingCoach` 继承公共 `GridRaceAssistant`，直接引用数据库、遥测采集、遥测分析、问题采集和游戏数据提供器。
- `TelemetryAnalyzer` 根据地图与分段，提取入弯、弯中、出弯、刹车建立、加速位置等摘要。
- 规则引擎可产生早刹／晚刹、刹车力度、加速时机等候选提示，大模型结合数据与指令生成说明。
- 原版逐弯提示通常使用上一完成圈；专项练习还能检查刚完成的赛段。
- 原版在位置事件触发时可能再调用大模型。因此“Sol 提前分析、本地触发、Live 播报”是拟议改造方向，不能说原版已经具备这套流程。
- 原版语音是识别、文字处理、合成的组合；原生 Live 双向语音需要改造，不是只改模型名称。
- 原版刹车倒计时依赖本地位置触发和声音提示，不是每个采样点都调用大模型。
- 地图存在但未定义分段时，会尝试根据遥测生成分段；手动校正仍有价值。
- 原版教练的场次记忆可保留到下一场开始前，不能直接等同于长期个性化训练记忆。

### 7.2 iRacing 的已知边界

| 项目 | 审查发现及影响 |
| --- | --- |
| 实际驾驶线路 | 原版相关实时遥测路径按圈内进度映射到固定地图坐标。同一进度会取得同一地图点，不能拿它证明不同圈实际横向走线的差异。未来做线路叠图需要另行确认轨迹来源。 |
| ABS／TC | 已审查的 iRacing 原生详细遥测写入路径将这两个通道写为 `n/a`。缺失不代表没有触发，也不能据此给出确定诊断。 |
| IBT 导入 | 原版导入实现把圈内时间字段留空，影响依赖时间轴的分析。这是该实现的限制，不是断言 IBT 本身无法提供任何时间信息。 |
| 胎压 | 原版文档提示行驶中的胎压数据有缺口；能够设置进站胎压不代表能实时读到可靠热胎压。 |
| 调校文件 | 原版自动调校文件编辑器的支持范围不包括 iRacing。文字建议与自动修改调校文件是两项能力。 |
| 延迟 | 状态刷新、详细遥测采样、位置触发、云端分析与语音各有时间开销，必须实测。 |

## 12. 拟定的标准使用流程

本节描述精简版完成后的产品流程，供继续讨论和实施使用，不代表原版已经自动实现这些步骤。默认目标是：用户启动教练并进入 iRacing 后正常驾驶，系统自动完成准备、记录、参考选择和分析；用户想追问某个弯时再主动提问。

### 12.1 第一次使用或第一次来到某条赛道

| 阶段 | 用户操作 | 软件行为 |
| --- | --- | --- |
| 启动教练 | 首次确认麦克风、耳机，进入练习。 | 读取已配置服务，显示游戏、语音和数据连接状态。模型设置不要求每次重复填写。 |
| 进入赛道 | 在 iRacing 中选择车辆和赛道，开始驾驶。 | 自动识别车辆、具体赛道布局和场次，检查地图、弯道分段和兼容的历史参考。 |
| 准备地图与数据 | 根据简短提示正常跑完整圈。 | 有可用地图就直接加载；没有时引导完成地图记录并尝试自动分段。原始录制、地图校验和教练数据准备均以实际完成状态为准。 |
| 建立初始参考 | 继续正常驾驶，无需导入或手动选择参考圈。 | 地图及分析数据就绪后，保存第一个数据完整、适合作比较的有效圈，作为临时个人基准。 |
| 积累可比较圈 | 再跑有效圈。 | 新圈先与本圈开始时选定的参考比较，再决定是否将新圈更新为后续圈的参考。 |
| 开始主动指导 | 正常驾驶，也可以要求暂停提示。 | Sol 根据已有数据筛选有依据的改进点；建议准备好后，在接近对应弯道时由 Live 简短提示。 |

首次新赛道可能需要先完成地图记录，再积累可分析的完整圈。准备阶段必须明确显示正在做什么，不能在无地图、分段不可靠或数据不足时假装教练已经就绪，也不承诺固定一圈就完成全部准备。分段明显有误时提供简单校正入口，正常流程不要求用户先手动画赛道或逐个填写弯号。

### 12.2 参考圈是什么以及怎样自动产生

参考圈是用于比较的一个已完成有效圈，可以来自用户自己，不必是职业车手的数据，也不代表最优驾驶。

建议采用以下默认规则：

1. 没有兼容历史数据时，先建立本场个人基准。第一个有效圈用于记录和单圈分析，无法与尚不存在的第二圈进行差异比较。
2. 后续圈比较速度、刹车和加速等指标时，使用已经存在的参考圈。默认从可用、条件可比的已完成圈中选择最佳有效圈。
3. 开始一圈时固定本圈使用的参考。该圈完成后先做比较，再更新下一圈的参考，避免拿新圈与它自己比较，或在一圈中途切换比较对象。
4. 重新进入同车、同赛道布局时自动检查历史参考。天气、车辆或其他关键条件明显不匹配时，重新积累基准；不只按最快圈速盲目选择。
5. 出站圈、未完成圈、数据损坏或明显不适合比较的圈不自动晋升为最佳参考；具体过滤规则在实施时验证。
6. 始终能查看当前参考的来源、圈次和圈速。手动指定已有圈、加载格式兼容的外部圈属于可选入口，不是首次开始练习的前置要求。

例如，没有历史参考时：第一个有效圈记录为基准；第二个有效圈与第一个比较；第三个有效圈使用前两个圈中适合作比较的最佳圈。若第二圈比第一圈慢，不会仅因它较新就替换最佳参考。

### 12.3 没有参考时能做什么

在详细数据和分段可用后，即使还没有可比较的参考，仍可说明本圈的实际表现，例如哪里多次补踩刹车、油门反复收放、方向修正较多，并基于可用数据提出试验性的改进建议。建议应明确区分观测事实、可能原因和需要下一圈验证的调整。

没有参考数据时，不声称已经知道相对某个高手损失多少时间，也不把猜测的理想刹车点当成测得的事实。使用自己的参考有助于理解差异和验证调整，但不能保证单凭个人最快圈就找到全局最优驾驶方式。

### 12.4 正常练习中的循环

1. 每圈自动采集、保存数据，生成逐弯摘要。
2. 圈完成后，Sol 比较本圈与参考，并结合已有建议判断变化。
3. 下一圈的提示提前准备；只对有依据、值得调整的弯道给出简短建议，避免每个弯都机械重复。
4. 用户随时可以问“上一圈哪里最慢”“为什么让我晚一点加速”“解释一下第五弯”，由 Live 接收，Sol 提供新的分析。
5. 用户可以暂停主动提示并继续记录。建议未准备好、已经过期或车辆已错过提示位置时，按调度规则跳过。

弯道选择默认为系统识别重点，用户无需逐个挑选。主动询问某一弯属于 B05；单独的 B08 专项训练管理流程仍未因此自动纳入。

### 12.5 回维修区、结束与下次继续

- 回维修区或结束练习时，提供简短总结：本次有效圈、最佳圈、主要改进、仍值得练习的内容。详细说明可通过语音追问，不要求在高速驾驶中听长报告。
- 自动保存有效遥测、地图、分段和可用个人参考圈；若展示摘要与原始数据的关联，应标明所依据的场次及圈次。
- 下次进入匹配的车辆与赛道布局时自动加载已有资料，并检查是否适合作为本次参考。
- 换车、换赛道布局或条件明显变化时重新检查和建立基准，防止混用不匹配数据。

最终用户主流程：**打开教练 → 进入游戏 → 正常跑圈并自动完成准备 → 自动建立或加载个人参考 → Sol 分析 → Live 对话与逐弯提醒 → 保存并复盘 → 下次继续。**

## 13. 指导可靠性与验证要求

用户明确提出：最担心指导内容不可靠，进而收到错误的驾驶建议。**可靠性应成为首版的核心验收目标。** 下述约束和验证方法是针对该关切提出的设计建议，尚未实现或完成效果验证。

### 13.1 当前能够作出的判断

- 系统可能提供错误指导。原版、Sol 或 Live 的名称不能作为内容准确性的保证；当前没有本项目的实测准确率，不能给出“达到某个可靠百分比”的承诺。
- 官方 7.3.2 教练文档明确承认可能编造内容，并指出缺少参考圈、分段不当、连续组合弯等情形会影响建议可信度。[原版教练限制](https://github.com/SeriousOldMan/Simulator-Controller/blob/9aa662664d83bce31151d1036fb32460e4023b06/Docs/AI%20Driving%20Coach.md#about-attention-deficits-hallucinations-and-other-funny-stuff) · [赛道与参考圈要求](https://github.com/SeriousOldMan/Simulator-Controller/blob/9aa662664d83bce31151d1036fb32460e4023b06/Docs/AI%20Driving%20Coach.md#track-layout)
- 自动记录到有效圈，只表示开始具备分析材料，不代表已经证明教练的诊断和动作建议正确。
- 自己的最快圈只是比较样本。某圈更快、某处刹车更晚，不能单独证明晚刹就是变快的原因，也不能直接推出用户下一圈应晚刹相同距离。

### 13.2 建议分开处理三类内容

| 类型 | 示例（仅作说明，不是对用户当前驾驶的诊断） | 验证方式及限制 |
| --- | --- | --- |
| 可测事实 | 本圈在某弯的刹车起点比参考更早，出弯速度更低。 | 用本地数值计算核对圈次、分段、对齐、单位和差值；事实本身也依赖数据质量。 |
| 原因推测 | 可能因为入弯处理影响后续加速。 | 明确表述为推测，检查其他可能因素，必要时保留多个解释。 |
| 动作建议 | 下一次尝试调整某一项操作，并观察整个弯及后续赛段的变化。 | 需要适用条件和实测反馈；不能从单个差值直接生成确定的最佳操作指令。 |

### 13.3 建议增加的约束

1. **事实由程序核对。** Sol 引用的指标应带有数据来源、场次、圈次、弯道、单位和比较对象；数值和早／晚、快／慢方向能够被本地代码复算。不存在的通道不能当成零值。
2. **先判断能否比较。** 检查地图分段、数据完整性、车辆及赛道布局、已知环境条件。条件不明或明显不匹配时，降低结论强度或不作该项指导。
3. **允许不作判断。** 没有参考或证据不足时，报告可核对的现象；不给出凭空推算的最佳刹车点、必然收益或“晚刹若干米”等强指令。不能用模型自报的置信度代替验证。
4. **限定主动提示内容。** 主动逐弯提醒仍保留在首版范围内，但候选建议应通过证据、适用条件和时效检查。优先验证少量明确的提示类型；没有合格建议时保持安静。
5. **验证完整动作链。** 比较整个弯和相关后续赛段，而非只追求某一瞬间更高的速度；改动建议后观察多个条件可比的样本，不能把单次提升当成因果证明。
6. **Live 保留结论含义。** 语音不得把“可能”说成“确定”，不得颠倒早／晚或增／减，也不得新增 Sol 没有依据的驾驶结论。提示词只是约束手段，仍要检查实际语音、打断、过期和错误弯号等情况。

### 13.4 建议调整第一阶段验收重点

功能打通和内容验证同时进行。先对真实历史遥测生成分析，核对依据和计算，再用有驾驶经验的人或教练审阅代表性的诊断与建议。建立包含正常圈、异常圈、缺失通道、不同条件、组合弯、错误分段和延迟结果的验证样本。

至少分别记录：数值及方向错误、无数据依据的结论、不适用的动作建议、应当拒绝判断却仍给出指导的情况、Live 转述改变含义，以及错误位置／过期播报。给出样本数和发现的问题，不用单一“准确率”掩盖不同错误。

只有对相应提示类型完成验证，才将其开放为默认主动指导；未通过的类型先保留为赛后讨论或停用。具体通过标准与样本范围需要在实现时明确，验证通过也不代表永远不会出错。软件能运行、语音流畅或模型彼此同意，都不能独立证明驾驶建议正确。
