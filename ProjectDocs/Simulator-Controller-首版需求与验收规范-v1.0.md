## 1. 文档约定

本文件将当前对话中已经确定的产品方向、已经说明的使用流程和可靠性要求转化为可检查的需求。它是首版验收范围清单，不等于原版的全部功能清单，也不表示任何测试已经通过。

- **已确认范围**：官方源码基础、个人自用、iRacing、A＋B＋M 核心、Sol 分析、Live 语音、主动逐弯提醒；线路叠图暂不做。
- **验收细化**：为上述功能能够正常使用而明确的数据隔离、参考圈规则、证据核对、故障处理和测试方法。属于本文件对已有需求的落地，不宣称用户逐字指定过每个工程细节。
- **待冻结参数**：此前没有约定的格式清单、误差容限、延迟和资源指标等，集中列在第 10 节。不得将未经实测或确认的数值写成已达成的性能承诺。
- 本文件中的“必须”“不得”用于判定相应需求是否通过。修改范围或标准时，应记录版本、原因和影响；不得因为实现困难而静默删减。
- 验收通过仅适用于报告列出的版本、数据、设备和场景，不代表所有赛车、赛道和驾驶条件下永不出错。

## 2. 产品目标与范围

### 2.1 产品目标

提供一个操作简洁的 iRacing 驾驶教练：用户启动软件并进入游戏后，正常跑圈即可积累数据；软件建立或加载合适的参考圈，由 Sol 分析，再通过 Live 对话和主动逐弯提示帮助用户理解差异、尝试调整并复盘。

首版以参考圈数据比较为核心能力之一，但不要求用户首次使用就具备外部参考圈。提前导入兼容的参考圈遥测是可选使用路径，开发交付中需要提供该入口。

## 3. 名词和数据边界

| 名词 | 本文定义 |
| --- | --- |
| 场次 | 一次进入练习、排位或比赛形成的驾驶会话，需要有可区分的标识。 |
| 有效圈 | 对所执行分析而言完整且可用的一圈。至少排除未完成、关键数据损坏、明确无效或明显不适合作参考的圈；“采集完整”和“适合作参考”应分别记录。 |
| 参考圈 | 用来比较的已完成圈，可来自用户自己或兼容外部文件，不等于最优驾驶标准。 |
| 兼容参考 | 车辆和具体赛道布局匹配，必要字段及单位可解释，已知关键条件不存在未处理的明显冲突。未知条件不得假装匹配。 |
| 弯道分段 | 分析使用的弯道、直道及其边界。编号可使用软件标识，但必须保持地图、数据、报告和语音一致；不得谎称自动编号必定等于官方编号。 |
| 分析依据 | 相关场次、圈次、弯道、参考来源、指标与计算结果。不是要求保存模型隐藏推理过程。 |
| 主动提示窗口 | 预先定义的本弯允许提示位置或时间区间，包含开始点和截止点。截止点必须服务于实际驾驶时机，不得为通过测试而移到弯后。 |
| 已播报 | 根据实际音频或播放记录确认用户可听到的输出，不能仅以 API 返回成功作为依据。 |

分析数据至少需要关联：游戏、车辆、赛道布局、场次、圈次、有效性、时间或距离坐标、可用通道、单位和数据来源。缺失值、估算值、导入值与实测值需要能够区分。

iRacing 原版已审查路径存在 ABS／TC 缺失、IBT 导入圈内时间留空，以及固定地图坐标不等于实际走线等限制。具体新版实现应复核字段；缺失数据不能通过默认为零“补齐”，本文件不要求支持游戏没有可靠提供的信号。

## 4. 标准业务流程

### 4.1 首次使用，没有任何参考圈

1. 用户启动教练，完成必要的音频及服务设置，进入 iRacing。
2. 系统识别车辆、赛道布局和场次，检查地图、分段及数据状态。
3. 若无可用地图，提示用户按要求正常驾驶，完成记录和分段准备；显示真实进度和失败原因。
4. 在准备就绪后记录第一个可用完整圈，允许查看本圈事实，并建立初始个人基准。
5. 第二个及后续可用圈与已存在的参考比较；系统自行识别重点弯道，用户不必逐个选择。
6. Sol 形成有依据的分析。合格且未过期的短建议在对应提示窗口由 Live 表达。
7. 用户可以追问、打断、暂停提示，记录工作继续进行。
8. 结束练习后保存数据并提供总结，下次进入兼容场景时检查并加载。

不以固定一圈或固定几圈完成建图作为既定承诺，但必须在满足事先声明的准备条件后进入可用状态，不能无期限停留在“收集中”。数据不足时不得假装已经完成分析。

### 4.2 首次使用，提前导入外部参考圈

1. 用户选择一份支持格式的参考文件。
2. 系统检查车辆、布局、字段、单位和完整性，展示参考来源及可用状态。
3. 合格文件可作为对应场景的指定参考；不合格文件给出具体原因，不能静默启用。
4. 用户进入游戏，系统仍要准备地图、分段和本车数据。
5. 用户完成可用圈后进行比较；已有外部参考不意味着系统已经了解用户尚未完成的驾驶。

“导入”是可选用户操作，不是可省略的已选功能。具体首版支持格式按第 10 节冻结，至少交付一种明确格式及兼容样例。

### 4.3 已有历史数据的日常练习

启动 → 自动识别 → 检查并加载兼容资料 → 正常记录 → 分析与语音指导 → 总结保存。

默认自动参考规则如下，属于本文件对无手工准备流程的细化：

- 无可用历史参考时，从本场已完成有效圈建立基准；随后从兼容候选中选择最佳有效圈。
- 一圈开始时固定该圈的参考版本。新圈完成后先比较，再更新后续圈的自动参考，不与自身比较。
- 用户明确指定的外部或历史参考不被静默覆盖；切回自动选择后才按自动规则更新。
- 用户在一圈中途更换参考时，显示“下圈生效”，不混用两个参考完成同一圈的比较。
- 已知条件明显不匹配时不自动启用；条件未知时说明限制，对依赖该条件的强建议保持克制。

## 6. 可靠性与运行质量要求

以下 Q 类需求与功能需求同等参与验收。通过检查和提示词可以降低错误，但不能据此承诺所有未来建议永远正确。

| 编号 | 要求 | 通过条件及证据 | 验收用例 |
| --- | --- | --- | --- |
| Q01 | 数值和事实可核对 | 展示、分析及语音引用的数值和早／晚、快／慢方向，能追溯到对应数据。与独立基准一致或在事先冻结的误差内；不得让 Sol 自己计算的答案同时充当测试标准。 | T13、T14、T15 |
| Q02 | 不确定性与适用性正确处理 | 区分事实、原因推测和动作建议。缺失通道、错车错布局、坏分段或未知关键条件时，不产生依赖这些信息的确定结论。拒绝判断不能被当成接口错误。 | T05、T07、T10、T12、T26 |
| Q03 | 驾驶建议有实质依据 | 对每种默认启用的提示类型，既有可给出具体建议的正例，也有必须限制或不建议的反例，并经过驾驶领域人工审阅。只会泛泛鼓励或全部保持安静不算完成教练功能。 | T19、T26 |
| Q04 | Live 准确转述 | 最终可听内容保留弯号、数值、操作方向、否定和不确定程度，不新增无依据的驾驶结论。以输出音频或人工听审证据核对，不能只检查发送给 Live 的文本。 | T17、T18 |
| Q05 | 提示时机和取消可靠 | 正向用例在冻结窗口内真正播报，关键内容在截止前表达完毕；负向用例跳过或停止。用户暂停、换场景和过期后不开始新播报，正在播放的内容按冻结的停止延迟终止。 | T03、T20、T21、T22 |
| Q06 | 凭据与记录保护 | 密钥不显示在普通界面、导出结果、日志、源码或交付包中。诊断记录脱敏；数据路径明确。无需保存所有用户原始麦克风音频。 | T27 |
| Q07 | 性能和运行稳定性可检查 | 记录实际语音延迟、分析等待、CPU／内存及游戏表现影响；达到测试前冻结的标准。正常长时流程无崩溃、数据串用或持续增长的任务积压。 | T28 |
| Q08 | 结果可追溯、可复测 | 保留版本、参数、输入、依据、结果及相关播放事件。涉及模型的关键场景至少重复 3 轮，逐次记录差异；这只是首轮测试下限，不是可靠性统计保证。 | T13、T26、T28 |

### 6.1 可靠性判定规则

以下情况在验收样本中出现即判该用例失败，修复后重测；不得用总体平均分掩盖：

- 使用错误的车辆、场次、圈次、布局或弯道给出驾驶指导。
- 捏造不存在的遥测通道、参考圈、数值或已完成动作。
- 将“比参考早刹”直接包装成已经证明“应晚刹相同距离”，而没有适用依据。
- 早／晚、增／减、左／右等关键含义颠倒，或把推测说成已证实事实。
- 超过本弯截止点后仍新启动该弯的动作提示，或暂停后继续播报排队内容。
- 输出明文密钥或损坏已保存的有效数据。

测试应同时包含正常可指导的样本。不允许通过禁用全部主动提示、全部回答“无法判断”来规避正向功能验收。

### 6.2 驾驶领域审阅

建议正确性不能只由同一个模型自评，也不能只依据某一圈变快。应由能核对该车辆和赛道驾驶逻辑的人员检查代表性样本；可以是具备经验的用户或其指定人员，不要求为了开发先购买专业服务。

审阅至少回答：观测是否真实、参考是否可比、原因是否过度推断、调整是否适用、是否忽略整个弯和后续赛段、证据不足时是否正确克制。存在未解决分歧的提示类型不得标为已验证并默认启用。

若只有软件功能测试通过、驾驶建议尚未审阅，结论只能写“功能测试通过，指导质量待验收”，不能写首版全面验收通过。

真实数据用于证明实际接入与分析能力；人工构造数据用于覆盖边界。只有模拟数据通过，不能代替真实 iRacing 验收。

本地已有候选参考 CSV，但尚未确认与本次导入器兼容，不能把文件存在记为 D03 已验收。正式验收需记录数据文件校验值或版本，避免输入变化后仍沿用旧结果。

## 9. 证据和判定方法

### 9.1 每项测试至少保存

- 用例编号、执行人、时间、程序版本、相关参数版本。
- 输入数据标识、场次／圈次／参考版本，必要时保存脱敏副本或校验值。
- 预期结果、实际结果、通过／失败／阻塞状态和说明。
- 相关本地计算、模型请求标识及返回摘要；无需保存模型隐藏推理过程。
- 涉及语音时保存测试输出音频、播放时间线或人工听审记录；涉及真实游戏时标明实机测试，回放结果单独标明。
- 问题编号、修复版本和重测结果；失败记录保留，不用新的通过记录覆盖。

### 9.2 独立数值基准

关键计算应在小规模可检查样本上独立核对。直接采样值按单位换算和显示舍入检查；导出的距离、分段时间、速度及驾驶输入摘要使用已说明的算法和误差容限。

误差容限依据采样精度、插值方式和显示粒度确定，并在测试前写入参数记录。不得用当前实现的输出反向设定标准，也不得把单纯复写同一段计算逻辑视为独立验证。

### 9.3 语音时序

至少记录：建议就绪、位置触发、提示截止、首段实际可听声音、关键内容结束、用户暂停、实际停止播放。

分别检查“有内容及时说出”和“该安静时没有说”。网络请求成功、Live 接受文本、字幕生成均不能单独证明及时播报。对于有实时要求的提示，必须有真实游戏中的对应证据。

## 11. 验收结果与完成标准

### 11.1 状态定义

| 状态 | 含义 |
| --- | --- |
| 未执行 | 没有可用测试证据。文档创建时所有用例均为此状态。 |
| 通过 | 满足冻结的条件，证据完整。 |
| 失败 | 实际行为与要求不符。 |
| 阻塞 | 账户、数据、设备、未冻结参数等导致无法完成检查；不能当作通过。 |
| 不适用 | 有明确的范围变更记录，并解释不再适用的原因。 |

### 11.2 首版整体通过条件

1. R01—R16、Q01—Q08 均有对应执行证据，所有适用用例通过。
2. 影响判定的 P 类参数已冻结；若仍有待定项，相关能力只能记为待验收。
3. 首次无参考、提前导入参考、历史续用三条路径均通过，不要求用户先拥有高手圈。
4. 真实 iRacing 的采集、分析、语音和主动提示流程通过；不能全部用模拟替代。
5. 可靠性正反例、驾驶领域审阅和实际语音核对完成；没有未解决的关键错误。
6. 有实际可用且已验证的主动指导类型；不能通过关闭所有指导绕过该项交付。
7. 提供可运行交付物、操作说明、已测范围、已知限制、测试记录和复现资料；包含用户能够使用的必要配置入口。

“全部用例通过”不等于对未来全部驾驶场景给出零错误保证。报告必须保留测试范围、样本数和限制，不使用没有证据的总体准确率或圈速收益承诺。
